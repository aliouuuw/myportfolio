## Contexte

Fin 2022, Bun émergeait comme une alternative ultra-performante à Node.js. Son modèle d'exécution en binaire unique, son pilote SQLite intégré et ses temps de démarrage instantanés promettaient de redéfinir le développement local. Fasciné par ce bond en avant, je me suis lancé dans la création de **BocalBun**—un moteur de développement et framework local-first, conçu pour aider les développeurs solos à structurer, construire et déployer des applications hautement performantes en quelques minutes.

L'objectif était de créer une colonne vertébrale opérationnelle cohérente : un moteur d'entités ultra-rapide avec sécurité au niveau des lignes (RLS) intégrée, des hooks de cycle de vie et des migrations automatisées, le tout s'exécutant nativement sur Bun et SQLite.

Après plusieurs mois de R&D intensive et une base de code magnifiquement structurée, j'ai pris une décision délibérée : **j'ai gelé le projet et j'ai tourné la page.**

Cette rétrospective n'est pas l'histoire d'un échec technique. C'est une exploration du jugement d'ingénierie—savoir quand arrêter de construire des infrastructures abstraites pour commencer à livrer des systèmes dont les entreprises dépendent réellement.

## La Vision : Une colonne vertébrale opérationnelle local-first

Beaucoup de frameworks modernes sont conçus pour des environnements cloud-native et serverless. Pour les développeurs qui construisent des outils opérationnels—particulièrement dans des régions comme l'Afrique de l'Ouest, où les capacités local-first, la performance sur des machines à ressources limitées et les architectures prêtes pour le mode hors-ligne sont cruciales—cette dépendance systématique au cloud est un anti-pattern.

BocalBun a été conçu pour résoudre cela. Ce n'était pas juste un routeur ou un template ; c'était un runtime de développement intégré qui packagait :

- **Un moteur d'entités (Entity Engine) :** Des définitions de schémas structurées qui associaient automatiquement les types TypeScript à une base de données SQLite embarquée.
- **Sécurité embarquée (RLS) :** Des règles de sécurité déclarées directement dans le schéma, garantissant que l'accès aux données soit restreint automatiquement sans logique redondante dans les contrôleurs.
- **Hooks événementiels :** Des effets secondaires réactifs (ex. déclencher une notification Slack lors du changement de statut d'un compte) attachés directement aux cycles de vie des entités.
- **Un CLI fluide :** Un utilitaire de développement pour les migrations automatiques, le seeding de schémas et l'exploration interactive via un REPL.

## Architecture

Le système était organisé autour d'un registre central d'entités qui gérait le cycle de vie des schémas relationnels.

```
┌────────────────────────────────────────────────────────┐
│                      BocalBun CLI                      │
│      (REPL interactif · Générateur de migration)       │
└──────────────────────────┬─────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────┐
│                    BocalBun Runtime                    │
│  ┌──────────────────────────────────────────────────┐  │
│  │                  Entity Registry                 │  │
│  │   - Validation de schéma                         │  │
│  │   - Pool de connexions SQLite                    │  │
│  └───────────────────────┬──────────────────────────┘  │
│                          │                             │
│  ┌───────────────────────▼──────────────────────────┐  │
│  │                   Row-Level Security             │  │
│  │   - Évaluation dynamique de contexte             │  │
│  │   - Règles d'accès embarquées (Policies)         │  │
│  └───────────────────────┬──────────────────────────┘  │
│                          │                             │
│  ┌───────────────────────▼──────────────────────────┐  │
│  │                 Lifecycle Hooks Engine           │  │
│  │   - Effets transactionnels sécurisés             │  │
│  │   - Dispatch d'événements (Pre/Post-commit)      │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

La base de code privilégiait des performances d'exécution optimales en s'appuyant sur les liaisons SQLite natives et ultra-rapides de Bun, et en utilisant l'analyse TypeScript statique pour éliminer les coûts de réflexion lors de l'exécution des entités.

## La Dérive : Quand l'élégance devient un piège

L'implémentation technique de BocalBun était une réussite. Le système était rapide, expressif et robuste. Cependant, à mesure que la base de code mûrissait, je suis tombé dans le piège de la "gravité du framework" :

1. **Résoudre le cas général :** Au lieu de construire une fonctionnalité métier spécifique, j'ai passé des semaines à concevoir une bibliothèque de validation générique capable de gérer n'importe quel cas d'usage hypothétique.
2. **La tuyauterie avant le produit :** L'attention s'est déplacée de "qu'est-ce que je peux construire avec cela ?" à "comment rendre l'API d'enregistrement des plugins plus ergonomique ?".
3. **La taxe de maintenance :** Lorsque les premières versions de Bun ont subi des modifications majeures et fréquentes de leurs API, j'ai passé plus de temps à adapter mes liaisons internes de bas niveau qu'à livrer des fonctionnalités.

J'avais construit un outil hautement sophistiqué qui n'avait qu'un seul utilisateur : moi-même. J'accumulais de la propriété intellectuelle, mais aucune responsabilité opérationnelle.

## Le Choix Difficile : Pourquoi j'ai arrêté

Le déclic s'est produit lorsque j'ai analysé mes objectifs de carrière à long terme. Je ne voulais pas être un mainteneur de framework passant son temps à chasser des étoiles sur GitHub et à trier des tickets d'assistance. Je voulais construire des logiciels opérationnels qui font tourner des entreprises.

J'ai comparé l'investissement requis pour rendre BocalBun prêt pour la production pour d'autres développeurs à la valeur de l'application de cette même énergie directement sur des problèmes d'affaires réels. Le choix était évident :

- **Intellectuellement satisfaisant, mais vide commercialement :** BocalBun était un excellent terrain d'entraînement, mais il résolvait un problème que j'avais fabriqué de toutes pièces.
- **Un fort impact dans le monde réel :** De vraies entreprises de mon réseau luttaient avec des mises à niveau complexes de leur ERP Odoo ou des opérations fintech fragmentées. Elles n'avaient pas besoin d'un énième framework Bun personnalisé ; elles avaient besoin de systèmes opérationnels qui fonctionnent.

J'ai gelé BocalBun, archivé le dépôt, et réorienté l'intégralité de mon attention.

## Ce que j'ai appris (et ce que cela m'a coûté)

Geler BocalBun m'a coûté des mois de développement pur, mais cela m'a apporté l'atout le plus précieux qu'un ingénieur puisse acquérir : **le jugement.**

- **Le filtre "Qui attend ?" :** Si personne n'attend ce que vous construisez, vous construisez un bac à sable, pas un produit. Aujourd'hui, avant d'écrire la moindre ligne de code, j'identifie précisément l'opérateur ou le client qui a besoin du résultat final.
- **Les systèmes plutôt que les abstractions :** J'ai arrêté de chercher à construire "la couche de base parfaite". Chez Everest Finance, j'ai consolidé trois surfaces numériques complexes en donnant la priorité aux types partagés, aux schémas stricts et à des modèles de bases de données relationnelles simples, plutôt qu'à des abstractions de frameworks personnalisés.
- **Savoir abandonner un coût irrécupérable (Sunk Cost Skill) :** Savoir quand s'arrêter est une discipline d'ingénierie. Continuer à écrire du code pour un projet qui ne s'aligne pas avec votre direction stratégique n'est pas de la persévérance—c'est un manque de focalisation.

BocalBun est gelé, mais son ADN continue d'irriguer ma façon de concevoir des systèmes. Il m'a appris à construire léger, à penser local-first, et—surtout—à accorder plus de valeur aux retours de déploiements réels qu'à la perfection architecturale.
