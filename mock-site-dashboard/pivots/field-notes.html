Field Notes

FIELD NOTE 01

Fintech systems fragment when schemas drift

At Everest Finance, the public website, internal CRM, and customer app were three separate codebases with no shared data contract. A field added to the website's account form never propagated to the CRM. The CRM tracked onboarding status the website could not read.

The fix was not more integration. It was making the database schema the contract. Shared Zod schemas validate at the API boundary and generate types for all three frontends. A change to the account model is now structurally impossible to handle inconsistently.

3 surfaces → 1 schema Next.js + React Native + PostgreSQL Sama Naffa app in hardening

FIELD NOTE 02

ERP migrations fail when validation is manual

Every Odoo migration I witnessed at ERGOBIT followed the same pattern: a functional consultant clicks through screens, eyeballs data, and declares the migration good. Then a computed field silently returns wrong numbers for two weeks.

The toolkit I built uses Robot Framework keywords that non-engineers can read, Playwright for the complex SPA interactions, and a smoke/full split so teams get a pass/fail signal in fifteen minutes instead of a full day of clicking.

39 tests × 9 suites Robot Framework + Playwright Azure DevOps CI

FIELD NOTE 03

Frameworks become traps when nobody is waiting

BocalBun had clean architecture, typed entities, RLS baked in, and audit trails. It also had zero users, zero revenue, and no distribution path. Every abstraction I added was debt I owed only to myself.

Stopping was the highest-leverage decision of that period. The same months redirected toward production Odoo work and later Everest generated more visible, trusted proof than any amount of framework polish could have.

Frozen, not abandoned Entity engine + RLS patterns live on in client work Bun / TypeScript / PostgreSQL

FIELD NOTE 04

Local businesses need workflow software, not app theater

Schools in Dakar run on WhatsApp groups and Excel. Bakeries track inventory in notebooks. A fancy mobile app does not solve this — a structured operations layer that respects existing habits does.

EduPlan and Gerpain were built by observing actual workflows first: how a school registrar schedules exams, how a bakery manager counts flour. The software follows the workflow. It does not replace it with a new interface to learn.

EduPlan — K-12 operations Gerpain — multi-bakery platform 6+ local clients across Dakar
FIELD NOTE 05

AI agents need repo memory, not prompts alone

When I started using AI coding assistants, the same pattern emerged: excellent first-session output, architectural drift by the fifth. Agents forget constraints, rename variables inconsistently, and introduce patterns that contradict existing conventions.

The solution is not better prompts. It is persistent repo context: AGENTS.md conventions, architecture decision records, manifest files that describe the system structure. The agent reads the manifest on every session. The human retains architectural control.

AGENTS.md pattern Architecture persistence Manifest drift detection
